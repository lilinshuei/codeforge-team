# 交接与证据标准

## 1. 一个合格的交接长什么样

```yaml
task_id: T-007
from: engineering-lead
to: quality-security-lead
status: ready
objective: 对登录链路做发布前质量门禁
inputs:
  - src/auth/login.ts
  - migrations/20261110_add_sessions.sql
  - 部署说明 docs/deploy.md
constraints: 不改接口契约；不新增运行时依赖；只允许在当前分支修缺陷
deliverable: 门禁报告 + 缺陷清单 + 放行结论
evidence_required:
  - 单元测试与集成测试的命令、输出、覆盖率
  - 登录/刷新/注销三条路径的实际请求与响应
  - 依赖漏洞扫描结果
  - 性能基线（P95 延迟、错误率）
acceptance:
  - 高危漏洞为 0，或逐条有书面豁免
  - 关键路径测试全绿
  - 回滚步骤可执行
risks:
  - 会话表迁移不可逆：需先备份
deadline: 2026-11-10 18:00
```

## 2. 一个不合格的交接

```yaml
to: 测试
content: 代码写完了，你测一下
```

问题：没有任务号、没有范围、没有验收口径、没有证据要求、没有风险和回滚。接活方只能猜，最后一定扯皮。

## 3. 证据等级

| 等级 | 证据 | 能证明什么 |
|---|---|---|
| L0 | “我检查过了” | 什么都不能证明 |
| L1 | 读了文件/看了代码 | 看到了，不代表能跑 |
| L2 | 构建通过、静态检查通过 | 语法和类型没问题 |
| L3 | 测试通过、接口返回、日志 | 行为符合预期 |
| L4 | 真实入口操作、截图/录屏、端到端回归 | 用户路径可用 |
| L5 | 生产/预发观测数据、回滚演练 | 可上线、可恢复 |

交付包至少 L3；涉及用户可见功能至少 L4；涉及数据迁移/发布至少 L5 或有等价演练。

## 4. 打回规则

打回必须包含三样：

1. 具体缺什么（对应任务卡的哪一项）。
2. 需要补什么证据（对应证据等级）。
3. 补齐后从哪一步继续（不要整包重来）。

不允许用“感觉不对”“再优化一下”打回。

## 5. 组长收活检查清单

- [ ] 任务卡字段齐全，验收项可逐条勾选
- [ ] 交付物路径真实存在，能打开
- [ ] 证据与验收项一一对应
- [ ] 风险、未覆盖范围、回滚方案写明
- [ ] 下一棒明确（谁、做什么、什么时候）
