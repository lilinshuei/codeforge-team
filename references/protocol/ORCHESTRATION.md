# 代码工坊专家团 · 通用编排协议 v1

这套协议是「团队」的可移植内核。平台适配器只负责把同一套角色、指挥链和交付契约翻译成各家的原生格式，不改变协议本身。

## 1. 组织与指挥链

```
项目开发部门主管（codeforge-team-lead）
├── 产品规划组（product-planning-lead） 9 人
├── 工程实现组（engineering-lead）       9 人
├── 质量安全组（quality-security-lead）  9 人
└── 体验交付组（experience-delivery-lead）8 人
```

硬规则：

1. 需求统一进主理人；主理人只派给四位组长。
2. 组长把组级目标拆成组员任务，组员只向组长交付。
3. 主理人只收「组级交付包」，不越级直接指挥专家。
4. 跨组依赖一律经主理人中转，不允许组与组私下改契约。
5. 谁产出、凭什么、谁验收，必须可追溯。

## 2. 六阶段流程与门禁

| 阶段 | 负责人 | 产物 | 出门条件 |
|---|---|---|---|
| 受理分级 | 主理人 | 任务卡：目标/范围/风险/验收口径 | 目标可观察，范围有边界，风险已分级 |
| 立项方案 | 产品规划组长 | PRD、交互与视觉方案、里程碑、验收清单 | 每条需求都有验收口径 |
| 架构实现 | 工程实现组长 | 架构决策、可运行代码、迁移脚本、部署说明 | 真实入口可启动，关键路径可跑通 |
| 质量门禁 | 质量安全组长 | 审查/测试/安全/性能/可访问性报告与放行结论 | 高危清零或有书面豁免，测试有证据 |
| 体验交付 | 体验交付组长 | UI 实现、动效、文档、上线、演示物料 | 用户可操作，文档可照着做 |
| 终验复盘 | 主理人 | 交付包、证据链、遗留风险、复盘 | 验收清单逐项有结论 |

任何阶段可以打回上一阶段，但必须写明「打回原因 + 需要补的证据」，不允许只说“不行”。

## 3. 任务卡（派活必填）

```yaml
task_id: T-001
from: codeforge-team-lead
to: engineering-lead
scale: lite | standard | full
objective: 一句话说明要达成什么可观察结果
inputs: 相关文件、接口、数据、上游交付包
constraints: 技术栈、时间、权限、不能动的东西
deliverable: 具体产物与格式
evidence: 需要什么证据（测试/日志/截图/接口返回）
acceptance: 可逐条勾选的验收项
risks: 已知风险与升级路径
deadline: 预期完成时间
```

缺任意一项，接活方应退回补齐，而不是靠猜开工。

## 4. 交付包（收活必带）

```yaml
task_id: T-001
owner: engineering-lead
status: done | partial | blocked
deliverable: 产物路径或链接
evidence: 证据清单（命令、日志、测试报告、截图）
acceptance: 逐条对照结果
risks: 遗留风险、未覆盖范围
next: 建议的下一棒（组/人/动作）
```

## 5. 启用档位与触发词

默认由主理人**自动判档**：按 `INTAKE.md` 六维评分（0~18），0~5 精简、6~11 标准、12~18 全量。开工前广播一行编队，不阻塞等待确认；用户点名档位时以用户为准。

### 三个档位

| 档位 | 规模 | 适用任务 | 执行方式 |
|---|---|---|---|
| 精简档（默认） | 主理人 1 + 组长 1~2 + 专家 2~4 | 改一个模块、审一个 PR、做一版方案、单点排雷 | 直接派活 |
| 标准档 | 主理人 + 2~3 个组 + 专家 6~10 | 一个完整功能、一次上线、跨前后端 + 审查 | 按阶段串行，组内并行 |
| 全量档 | 40 人全部纳入计划：主理人 + 4 组长 + 35 专家 | 从 0 到 1 的完整产品、多个并行子系统、组织级多线交付 | 分波次推进，每波全员有任务卡 |

**全量档 ≠ 40 个并发线程。** 它的含义是：40 人全部进入计划、全部有任务卡、全部有交付物或明确“本轮不参与”的书面理由。执行按 `plan → build → gate → deliver` 分波次，同一波内再并行；实际并发上限服从宿主（默认不超过 4 个组员同时运行，Codex 受 `max_threads` 限制）。

### 触发词（用户说任一即命中）

全量档：

- “全量启用 / 40 人全开 / 全团开工 / 全员上阵”
- “按组织级多线交付跑”
- “四个组全部进入交付，一个都别省”
- 点名式：“产品、工程、质量、交付四组全量，每人都有产出”

标准档：

- “标准档 / 多组协同 / 走完整流程”

精简档：

- “精简档 / 最小团队 / 先别兴师动众”

强制全量：

- “强制全量”——即使任务很小也 40 人全开；主理人只提醒一次成本，然后照办。

### 全量档的硬要求

主理人开工前必须给出三项，缺一不得宣布“全量档已启用”：

1. **40 人分工表**：每个角色一行，写任务卡编号、所属波次、交付物。
2. **波次图**：每波谁上、依赖是什么、哪些角色本轮不参与及理由。
3. **门禁计划**：每波结束由谁验收、验收证据是什么。

### 自动判档与升级

- 评分细则、覆盖规则、边界取档见 `INTAKE.md`；边界分数向上取一档。
- 计划阶段出现 ≥3 个组有真实交付物、有效任务卡 ≥9 张、新增生产或安全要求、用户追加范围 → 自动升一档并广播，不等待确认。
- 降档只在波次边界释放无任务角色，不打断已在跑的工作。
- 判不出来时按最接近的显式范围取档，不得因为犹豫而默认真全开。

用户明确点名档位时，以用户为准；用户说“强制全量”时不再反复劝。

## 6. 并行与依赖

- 无依赖任务可并行；有依赖必须显式写 `depends_on`。
- 并行上限由运行时决定（Claude/Codex/DSH 各自有线程/深度限制），默认不超过 4 个同时运行的组员。
- 共享文件、数据库迁移、接口契约变更属于冲突热点，同一时间只允许一个 owner。

## 7. 反模式

- 主理人亲自写代码/写 PRD/做视觉稿。
- 组长把任务原样转发给组员，不拆验收口径。
- 组员直接找别组的人改接口。
- 用“已完成”代替证据。
- 一次开 40 个 Agent 但没有依赖图和验收门禁。

## 8. 完成定义（Definition of Done）

1. 有真实入口和启动命令，能跑。
2. 关键路径有测试或可复现验证，证据齐全。
3. 高危安全问题清零或有书面豁免。
4. 文档、回滚方案、负责人明确。
5. 验收清单逐条有结论，遗留风险写明。
