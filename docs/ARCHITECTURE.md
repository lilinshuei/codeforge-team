# 架构说明

CodeForge 把「团队」拆成两层：**组织协议** 与 **平台适配**。协议定义谁负责什么、怎么交接、什么算完成；适配层只负责把同一套定义翻译成各宿主的原生格式。

```text
             ┌──────────────────────────────────────────┐
             │              组织协议（稳定）              │
             │  指挥链 · 六阶段 · 任务卡 · 交付包 · 门禁   │
             └──────────────────────────────────────────┘
                                │
        ┌───────────────┬───────┴───────┬───────────────┐
        │               │               │               │
   原生子 Agent      Skill 驱动      角色扮演       宿主适配层
   （保真最高）      （保真中）      （最通用）      （可替换）
```

## 1. 为什么是三层汇报，而不是扁平的 40 人

40 个角色如果都直接向主代理汇报，主代理的上下文会被 40 份交付物撑爆，也很难判断谁该等谁。三层结构解决三个问题：

1. **上下文隔离。** 组长只汇总本组，主理人只收组级交付包。
2. **契约稳定。** 跨组依赖必须经主理人中转，避免两个组私下改接口。
3. **责任可追溯。** 每张任务卡都有 `from` / `to` / `acceptance`，出问题能定位到阶段和角色。

硬规则写在 [`references/protocol/ORCHESTRATION.md`](../references/protocol/ORCHESTRATION.md)：

- 需求统一进主理人；
- 主理人只派给四位组长；
- 组长拆给组员，组员只向组长交付；
- 跨组依赖经主理人中转；
- 谁产出、凭什么、谁验收，必须可追溯。

## 2. 六阶段为什么这样切

| 阶段 | 解决的问题 | 失败模式 |
|---|---|---|
| 受理分级 | 目标是否可观察、范围是否有边界 | 需求含糊就开工，越做越大 |
| 立项方案 | 每条需求是否有验收口径 | 做完了才发现不是用户要的 |
| 架构实现 | 是否有一个真实可启动的入口 | 只有片段代码，没有可运行系统 |
| 质量门禁 | 正确性、安全性、性能是否有证据 | 自己说「没问题」 |
| 体验交付 | 用户是否能操作、文档是否能照做 | 功能能跑，但没人会用 |
| 终验复盘 | 验收清单是否逐项有结论 | 遗留风险无人认领 |

阶段之间可以回退，但回退必须写「原因 + 缺什么证据」。这条规则的作用是：把「不行」变成可执行的返工指令。

## 3. 判档：为什么不让用户先选

让用户先选「精简 / 标准 / 全量」，实际会把决策成本推给最不了解执行细节的人。CodeForge 改成先判档、再广播、直接开工：

- 六个维度各 0~3 分，总分 0~18；
- 0~5 精简、6~11 标准、12~18 全量；
- 边界分数向上取一档；
- 执行中出现「≥3 组有交付物 / 任务卡 ≥9 / 生产或安全要求」自动升档；
- 用户点名档位时以用户为准。

判档结果写进首张任务卡的 `scale` 字段，后续交付包可追溯。

**全量档的定义是「40 人进计划」，不是 40 个并发。** 并发上限仍由宿主决定；每个角色要么有任务卡，要么有「本轮不参与」的书面理由。

## 4. 证据链

交付包固定包含：

```yaml
task_id: T-001
owner: engineering-lead
status: done | partial | blocked
deliverable: 产物路径或链接
evidence: 命令、日志、测试报告、截图、接口返回
acceptance: 逐条对照结果
risks: 遗留风险、未覆盖范围
next: 建议的下一棒
```

「带证据」不是形式主义，它防的是三种常见失败：把一次成功当成稳定、把局部通过当成整体通过、把「我检查了」当成检查结果。

## 5. 三种运行模式

| 能力 | A 原生 | B Skill | C 角色扮演 |
|---|---|---|---|
| 角色提示词 | 完整 | 完整 | 完整 |
| 独立上下文 | 有 | 部分 | 无 |
| 真并行 | 有 | 视宿主 | 无 |
| 三层汇报 | 原生/代转 | 代转 | 显式切换 |
| 工具权限隔离 | 平台级 | 提示词级 | 提示词级 |
| 证据链与门禁 | 完整 | 完整 | 完整 |

选择原则：能用 A 不用 B，能用 B 不用 C。但无论哪一档，交付契约和验收门禁必须一致——这是协议层不随宿主变化的部分。

## 6. 扩展点

- **加角色**：在 `references/team.json` 的 `members` 增加记录，在 `references/agents/<id>.md` 写提示词，保证 `id` 唯一、`reports_to` 指向存在的角色、`group` 属于四个组之一。
- **改组**：新增组需要同时更新 `groups`、对应组长、以及 `ORCHESTRATION.md` 的指挥链。
- **改流程**：优先改 `protocol/` 下的协议文件，而不是把规则散落进角色提示词；角色只描述职责边界。
- **换宿主**：只改适配层（放哪里、怎么派子 Agent），不改协议。

## 7. 非目标

- 不做安全沙箱。权限隔离由宿主负责。
- 不替代人工验收。高危动作仍应由人确认。
- 不保证 40 个角色同时在线。它保证的是「有任务卡、有交付物或有理由」。
